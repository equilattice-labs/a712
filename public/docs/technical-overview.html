Technical overview · Author rewards v2

18 September 2026Robinhood Chain TestnetIndependent project

Implementation review · 18 September 2026 · Author rewards v2 and preserved wallet pilot

Voxdue is a Vue 3 application with a main author-rewards dashboard and a separately usable wallet-directed pilot on Robinhood Chain Testnet. Author rewards use native test ETH or a six-decimal tUSD demonstration token, public notes, a fixed 90-day deadline and a 3% fee on successful claims. The delivered X service verifies immutable account IDs and binds wallet proofs, but remains disabled without operator credentials; real X authentication has not been validated. The wallet pilot requires an explicit recipient address and never verifies authorship.

The contract accepts native test ETH with the zero token address or the single immutable supported tUSD address. Native funding must match the supplied amount exactly. Token funding uses SafeERC20 and verifies the escrow's exact balance increase, rejecting unsupported or unexpected transfer behavior. The UI requests only the required allowance for a token reward. The demo token faucet mints 1,000 tUSD per wallet per 24 hours; it requires test ETH for gas and has no commercial redemption promise.

The contract records payer, token, amount, expiry, status, numeric post and author IDs, and the public note. Reward numbering is independent of both earlier escrows. The sender has no authority to claim for the author. The attestor authorizes a fixed payout wallet; any transaction sender may relay that authorization, but cannot substitute a different recipient. The EIP-712 domain includes the specific v2 contract and chain. One successful claim or refund makes subsequent settlement impossible.

The v2 server uses /api/v2/x/post, /api/v2/wallet/challenge, /api/v2/rewards/:id/claim and /api/v2/rewards/:id/relay. Its one-use wallet challenge binds the origin, chain, contract, reward, X account and payout wallet. It re-reads the onchain reward and verifies its post's actual author through the official X API before signing. Real X credentials remain required even if the contract, signer and relayer are present.

Optional sponsored claims use an explicitly configured relay key and a funded gas budget. The service enforces a cap on estimated transaction gas cost, a gas-unit bound, a persisted daily budget, rate controls, per-reward single-flight work and a serialized transaction queue. Sessions remain in memory, and the budget uses a local file; production needs reviewed shared storage, locking and transaction recovery. The app must not advertise unlimited or guaranteed free gas. Sender funding, token approvals, faucet requests and refunds are ordinary wallet-paid transactions.

Read-only statistics and reward feeds come from the contract, with separate native/token accounting. Paginated feeds inspect a bounded number of reverse-ordered reward IDs and return a continuation cursor, including for sparse sender/author filters. A page can be empty while more history remains. Synthetic settlement tests are engineering activity, not customer traction. Public notes are rendered as text; users must avoid private information because chain history is public and cannot be erased.

The v2 source, local tests and synthetic testnet settlements do not establish production readiness, real X ownership verification, official USDG integration or independent security review. The earlier contracts below remain unchanged, with their distinct fee and expiry rules preserved.

2. System boundaries

The browser renders the Vue experience and requests wallet authorization. The wallet signs and submits transactions. Public reads use the Robinhood testnet RPC. The immutable escrow contract owns settlement rules; an explorer provides an independent view of receipts and source.

The wallet pilot requires no backend or account database. The main author integration adds an optional X identity backend and gas relayer, disabled until explicitly configured. There is no email collection, analytics integration or token sale. Browser-wallet connection by itself is not a server-side login or proof of an X identity.

3. Wallet and browser flow

The wallet module listens for EIP-6963 provider announcements and requests provider discovery. It falls back to window.ethereum when appropriate. Connecting calls eth_requestAccounts; the app listens for account and chain changes and refreshes its visible state.

Before a write, the app checks the wallet chain ID. It requests wallet_switchEthereumChain, and, if the network is unknown, supplies wallet_addEthereumChain with the official testnet parameters before checking the chain again. Rejected requests produce a recoverable error. The selected wallet signs transactions through ethers BrowserProvider.

Disconnecting clears Voxdue's in-memory account and provider state and removes the selected provider's listeners. It does not revoke the wallet's site permissions; the user manages those in the wallet.

Funding validation

The form accepts HTTPS URLs on x.com, www.x.com, twitter.com, or www.twitter.com with the conventional /handle/status/numeric-id path. It extracts a 1–30 digit post ID. This is a syntax check, not an API lookup; the post might not exist, and its author is not verified.

The user enters a nonzero EVM recipient address, a positive amount up to 0.1 test ETH in the UI, and a claim window. The current presets are 1 hour, 1 day, 7 days, and 30 days. The default is 7 days. A checkbox makes the payer acknowledge responsibility for the recipient wallet.

The UI derives the deadline from a recent chain block timestamp, falling back to the browser clock if that read returns no block. The transaction's actual block timestamp determines whether the contract accepts the deadline. Wallet signing delays can shorten the remaining claim window or invalidate an unusually short deadline.

The 0.1 ETH limit is an interface safeguard, not a contract-wide limit. Direct contract calls can fund any positive amount. All assets in this deployment are test ETH.

Receipt and settlement

After submission, the app shows the transaction hash and waits for a confirmed receipt before announcing funding success. It decodes RewardCreated to obtain the reward ID, reads the reward, and shows its status, amount, payer, recipient, post ID, and expiry. Receipt links use ?reward=<id> on the current site and can be copied for manual sharing.

The claim/refund view uses public RPC reads. It presents the permitted action according to the connected wallet, stored reward state, and displayed time, adjusted from a recent chain block. This clock is only a display aid; the contract decides eligibility using block time. A transaction can therefore be rejected near an expiry boundary even if a stale UI showed an action.

There is no automatic social post, mention, or message. Sharing a receipt remains the user's choice.

4. Contract semantics

Each reward stores the payer, recipient, amount, expiry, status, and numeric post ID. Reward IDs increase from 1. rewardCount tracks the number created; totalEscrowed tracks outstanding unsettled value.

MethodExact behavior
createReward(postId, recipient, expiresAt)Payable. Requires 1–30 numeric characters, recipient neither zero nor the contract itself, positive value, and expiry between block time + 5 minutes and block time + 30 days.
claimReward(rewardId)Active reward only. Caller must be the immutable recipient. Requires block time strictly before expiry. Pays the full amount.
refundReward(rewardId)Active reward only. Caller must be the original payer. Requires block time at or after expiry. Pays the full amount back.
rewards(rewardId)Public record; remains available after settlement.
rewardCount()Number of rewards ever created.
totalEscrowed()Recorded outstanding escrow obligations.

Statuses are 0 Missing, 1 Active, 2 Claimed, and 3 Refunded. Expiry does not mutate storage by itself; an expired unclaimed reward remains Active until refunded. The website labels that condition as ready for refund.

Events are RewardCreated, RewardClaimed, and RewardRefunded. Settlement updates state and accounting before an external native-ETH transfer and uses OpenZeppelin ReentrancyGuard. A failed transfer reverts the complete transaction, leaving the reward unsettled.

There is no administrator, owner role, upgrade proxy, protocol fee, administrative withdrawal, emergency pause, recipient-change function, or generic payable deposit entry point. That narrow surface reduces privileged behavior but also means there is no operator rescue mechanism. A new feature requiring different authorization needs a separately deployed version.

Important edge cases

  • A recipient contract that refuses ETH cannot claim successfully. The original payer may refund after expiry.
  • A payer contract that refuses ETH cannot receive a successful refund. The interface is intended for ordinary EVM wallets.
  • Only one terminal action can succeed. Claimed and refunded rewards cannot be paid again.
  • Unsolicited ETH forcibly sent to the contract is not credited to a reward and has no recovery method.
  • A syntactically valid post ID does not establish existence, authorship, consent, content rights, or the identity of the recipient.
  • Network and wallet requests can fail. Users must check receipts rather than infer success from a button click.

5. Tests and operational tooling

The contract suite runs on an isolated local EVM without reading the deployer key or sending remote transactions. Eight tests cover validation and accounting, recipient authorization, single settlement, payer authorization and refund timing, expiry boundaries, missing rewards, reentrancy, and transfer-failure rollback. An ABI assertion checks the absence of administrative withdrawal and generic payable deposit functions.

The recorded live smoke test confirms create → claim and create → expiry → refund on the deployed testnet contract. It uses the same controlled deployer wallet as payer and recipient; this is a settlement smoke check, while distinct-role authorization is exercised in local tests. It is not a complete external-user wallet compatibility study.

The optional X integration adds four local contract tests and fourteen backend tests using mocked X and chain responses. They cover typed authorization and identity/session protections, including wrong-author rejection, wallet proof, replay, CSRF/origin checks, OAuth state/PKCE, rate limiting and post URL validation. These tests do not validate real X credentials or authenticate a real author.

6. Optional X-author integration: delivered, not activated

The repository also contains XStudio.vue, an Express 5 identity API, and a separate XPostRewardEscrow deployed at 0xfa0095Af3f8129710E803CE5c9855A4d1db1633F. The deployment transaction is at block 121190852. This is independent of the wallet-only escrow, with separate reward numbering and ?xReward=<id> receipts.

The X contract also received explorer Pass - Verified source status. A self-funded synthetic attestation smoke check created X reward 1 and claimed it, moving 0.000001 test ETH and leaving no outstanding X escrow at that check. The attestation was synthetic: no live X login or actual author attribution was performed. Evidence is in deployment/x-source-verification.json and deployment/x-smoke-test.json.

No operator X credentials were supplied. Real X sign-in and author claims are not active and have not been validated against real X accounts. The app gates post resolution, funding and claims on API readiness. Reading an existing X escrow and refunding it after expiry do not require X login.

Identity and wallet verification

The server resolves posts through https://api.x.com/2/tweets/{id} using an operator bearer token. OAuth uses https://x.com/i/oauth2/authorize, the official token endpoint, PKCE with S256, and only tweet.read users.read scopes. It obtains the authenticated numeric ID from /2/users/me; it does not trust a typed handle. Access and refresh tokens are not retained in the pilot's session.

A session lasts one hour and is stored in memory. HTTPS uses an HttpOnly, Secure, SameSite=Lax, __Host- session cookie. The session identifier rotates after OAuth. State is single use and expires after ten minutes. State-changing API calls validate a CSRF token and origin. Rate limiting and a request-size limit apply.

The claimant signs a one-time EIP-191 wallet message bound to site origin, chain 46630, X user ID, reward ID, receiving address, nonce and a five-minute expiry. The server consumes the challenge before asynchronous claim work. It reads the reward from chain and freshly resolves the original post through X. The stored author ID, authenticated X ID, and freshly fetched actual author ID must all agree.

Exact onchain authorization

The server issues an EIP-712 Claim(uint256 rewardId,address recipient,uint64 deadline) signature. The domain is Voxdue X Rewards, version 1, chain ID 46630, with the separate X escrow as verifying contract. Authorization is limited to three minutes or the reward expiry minus one second, whichever is sooner. The caller must be the authorized recipient wallet.

The contract signature contains the reward ID, recipient and deadline. Post and author IDs are immutable fields referenced through that reward; they are not separate typed-signature fields. The wallet challenge has a nonce; the typed claim does not. Reward terminal state prevents successful claim replay, while the domain prevents cross-contract and cross-chain replay.

This contract checks numeric ID syntax at funding. It cannot establish that an author ID is correct on its own; correctness depends on the server's API checks. A caller bypassing the UI could create a mismatched reward that the server will refuse to authorize, leaving refund after expiry as the available settlement path.

Trust and operating limits

The attestor is immutable: 0x8b3283a9291373069f79508da59001e807bB394F. It can authorize any active X escrow. Server compromise or signer theft could therefore redirect funds; the system is not fully trustless. There is no signer rotation, upgrade, admin withdrawal or emergency pause. A future production design needs independently reviewed key custody, limits, incident response and migration.

The server is a single-process testnet integration. Sessions and rate limits are in memory; restart ends sessions, and horizontally scaled deployment needs shared stores. It binds to 127.0.0.1:8787 by default. The canonical local website is http://127.0.0.1:5177, with /api proxied to that server. HTTPS production access requires an appropriate reverse proxy with /api routed to the same public origin as the frontend. There is no hosted backend provided by this repository.

The required operator values are PUBLIC_ORIGIN, X_CLIENT_ID, X_BEARER_TOKEN, and one matching attestor key source: CLAIM_ATTESTOR_PRIVATE_KEY or CLAIM_ATTESTOR_KEY_FILE. Supply X_CLIENT_SECRET when the X application's client type requires it. RH_TESTNET_RPC_URL and PORT are configurable. Server startup checks chain ID, deployed code, and attestor address; these checks do not prove that X credentials or real-account OAuth work.

See the X identity setup guide for exact endpoints, setup steps, and activation gates. The wallet pilot remains usable without this integration.

7. Production gaps and source references

Before any real-asset release, complete legal/entity scoping, an independent security audit, operational monitoring, provider-backed RPC/indexing, incident procedures, final asset and fee policies, and capped-user validation. V2 already implements a 3% claim fee, a demo token and configurable sponsorship; canonical real-asset support, funded production sponsorship, embedded wallets and campaign billing remain launch-gated. Robinhood mainnet uses a different chain ID; the current deployment is testnet only.

Official references checked during this build:

  • Robinhood Chain overview — EVM Layer 2 architecture and ecosystem disclaimer.
  • Network configuration — testnet chain ID, RPC and explorer; public endpoints are rate-limited.
  • Smart-contract deployment — deployment and verification guidance.
  • X OAuth 2.0 with PKCE — requirements for activating and validating the delivered optional authentication flow.
  • X API pricing — observed post-read and user-read cost inputs for the business plan.
